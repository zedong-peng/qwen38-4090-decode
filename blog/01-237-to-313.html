237 → 313 tok/s: speculative decoding of a 27B model on one RTX 4090

Every number here comes from one box: 4× RTX 4090, one card per run, 450 W, PCIe Gen3. Benchmark: Spec-Bench, all 480 prompts, concurrency 1, greedy, 256 new tokens.

  • Qwen3.8-27B with a DFlash2 block drafter now decodes Spec-Bench-480 at ≈313 tok/s. The release container runs at 237.6 tok/s on our engine branch, and at 179.0 tok/s on stock Cinference with its default 7-token chain.
  • The quantized target is closer to the FP32 reference than the release on every fidelity metric: KL64 0.0618 vs 0.0668, top-1 0.9256 vs 0.9250, PPL 3.21 vs 3.29. Speculative decoding is lossless with respect to that target.
  • Two levers did it: fewer weight bytes per round, through better quantization, and kernels that stream those bytes at 850–950 GB/s. Most of the late gains were only visible because 0.3% differences could be measured reliably.

What a round costs

Qwen3.8-27B is a hybrid: 48 Gated DeltaNet (GDN) layers and 16 attention layers. One decode round works like this:

  • The drafter proposes a 16-node tree.
  • The target verifies the whole tree in one forward pass.
  • The longest matching path is accepted, plus one token from the target.

At ≈5.4 accepted tokens per round, tok/s is 5.4 divided by the round time. Each round streams the whole quantized target and drafter once, about 12 GB, so on a 1 TB/s card the round is mostly a memory-bandwidth problem.

The ledger

Each step was adopted only after a paired A/B (described below). Steps that change the target's numerics also had to pass a fidelity check against FP32.

Quantization was the biggest lever, and quality went up, not down. The release container uses round-to-nearest Q4/Q5.

  • GPTQ with act-order and a clip search beats it already at all-Q4, which is fewer bytes than the release.
  • End-to-end scale tuning trains only the per-group scales against the BF16 model's outputs. That buys enough KL headroom to move more projections to Q3.
  • Code is 4× more sensitive than prose. Top-1 agreement, not KL, ends up being the binding constraint.

A 3-bit screen in front of the LM head. The 248k × 5120 head is first streamed through a 3-bit "screen", which keeps the top-32 candidates per column, and only those candidates are rescored exactly. On its own, the screen was output-identical on all 480 prompts. It runs at the DRAM roof: 927 GB/s at T = 1, 895 GB/s at T = 16.

Q3 kernels are limited by DRAM access pattern, not arithmetic.

  • Removing the MMA, the dequantization or the scale math from the Q3 GEMM saved at most 1.3 µs.
  • Removing all compute made it slower, because more resident CTAs scatter requests across more DRAM pages.
  • Repacking each pipeline stage into one contiguous tile was 5% faster, with bit-identical outputs.

The drafter is free to be imprecise. Its precision cannot change the output, only acceptance.

  • Q4 and Q3 drafter projections paid off once the GEMM routes ran them at full bandwidth.
  • Fine-tuning the drafter on the target's own outputs gave +1.4% acceptance once. More rank, more epochs, soft labels and new data all landed in the same place.

Quality: measured against FP32, not against the release

Every target change is scored on 46,059 next-token predictions: 44 windows of 2,048 tokens of prose and code. The reference is FP32 compute over the BF16 checkpoint, layer-streamed through the transformers modules on the same 24 GB card. The metrics are:

  • KL64: KL(ref‖candidate) on the reference's top-64 support, using the candidate's exact logits there;
  • top-1 agreement;
  • perplexity.

The bar for adoption is "better than the release on every split and metric". Top-1 has the least headroom: the current target clears it by about 25 of 46,059 predictions.

A non-bit-exact kernel change, such as FP16 GDN state or a fused norm, flips about 200 near-tie predictions in each direction, which moves top-1 by about ±20. Rounding the carried GDN state to 5, 7, 8, 10 or 16 mantissa bits costs 10–25 agreements regardless of the precision. That looks like noise around a lucky baseline, not damage. The next post is about measuring the decode path itself, which the prefill-based tool never runs.

Measuring 0.3%

Most of the late gains are 0.3–1%, and run-to-run noise on an unforced Spec-Bench run is larger than that. It is also worse than noise: a near-tie flip changes which continuation gets generated, and with it acceptance and tok/s. Four things worked:

  1. Forced text. The engine can replace the target's greedy token with a reference id at each position (NINFER_FORCE_TOKENS). Every configuration then walks the same 480 texts, so round time is compared on identical tokens.
  2. A B A B on one GPU, with the other GPU's load held constant and no builds anywhere on the box. A niced 8-job build once made the same configuration read 0.9% slower. A→C and B→D measure the drift, often 0.1–0.3%, which is as large as the effect.
  3. A paired bootstrap per prompt gives the confidence interval on ms/round, tok/step and tok/s.
  4. nsys per-call kernel medians explain each result. nsys inflates host-side time severalfold, so host costs are priced from unprofiled request logs instead.

What did not work

  • Trellis quantization (EXL3). Matching our scalar quality needs ≈3.75 bpw, which is −9% bytes at best, and its decoder is slower.
  • A 32-node verify tree. +10% acceptance against +10–15% round time.
  • Side work on a second stream. GDN and attention kernels share DRAM and stretch each other one-for-one.
  • Grid and placement tricks. SM-balanced GEMM grids, prefetch.global.L2 on Ada, NUMA pinning and splitting the CUDA graph all measured null.
  • A 2-bit head screen. Its top-1 recall is 0.987.
  • RMSNorms folded into GEMM epilogues through a cross-CTA reduction. The atomics landing on a single L2 line cost more than the 80 norm launches they removed.
