# 237 → 313 tok/s: speculative decoding of a 27B model on one RTX 4090

*Draft, 2026-10-05. Numbers are from one box (4× RTX 4090, one card per run, 450 W, PCIe Gen3). Everything below is
measured there unless marked "reported".*

**TL;DR**

- Qwen3.8-27B with a DFlash2 block drafter decodes Spec-Bench-480 at **≈313 tok/s** on a single RTX 4090. The
  release container runs at 237.6 tok/s on our engine branch, and at 179.0 tok/s on stock Cinference with its default
  7-token chain. Setting: concurrency 1, greedy, 256 new tokens per prompt.
- The quantized target is now **closer to the FP32 reference than the release** on every fidelity metric
  (KL64 0.0618 vs 0.0668; top-1 0.9256 vs 0.9250; PPL 3.21 vs 3.29). Speculative decoding itself is lossless with
  respect to that target.
- Two levers moved the number:
  - fewer weight bytes per round, from better quantization (GPTQ, end-to-end scale tuning, Q3 where it is cheap);
  - kernels that stream those bytes at 850–950 GB/s.
- A third skill is what made most of the later gains visible at all: measuring 0.3% differences reliably.

## The machine we are optimizing

One decode round verifies a 16-node draft tree in one forward pass of the target:
- Qwen3.8-27B is a hybrid: 48 Gated DeltaNet layers and 16 attention layers.
- The drafter proposes the tree, and the target accepts the longest matching path plus one token.

At ≈5.4 accepted tokens per round, tok/s = 5.4 / round time. A round streams the whole quantized target and drafter
once, about 12 GB, so on a 1 TB/s card the round is mostly a memory-bandwidth problem:

| per round (nsys, 46 steady rounds) | µs |
|---|---|
| weight GEMMs (287 launches) | 14,500 |
| LM-head screens (target verify + drafter proposal) | 920 |
| RMS norms | 530 |
| attention (16 layers) | 340 |
| GDN recurrent record (48 layers) | 330 |
| GDN state fold | 300 |
| other | 230 |
| idle between kernels | 250 |
| **span** | **≈17,400** |

So there are only two ways forward:
- read fewer bytes per round without losing quality;
- get more accepted tokens out of each round.

The rest is overhead, worth ≈15% at most.

## The ledger

Each step was adopted only after a paired A/B (below) and, for anything that touches the target's numerics, a
fidelity check.

| step | Spec-Bench-480 tok/s |
|---|---|
| stock Cinference (Ada port), release container, default 7-token chain | 179.0 |
| our branch, same container: Ada fixes, small-T GEMM tuning, evict-first weight fills, 16-node verify tree | 237.6 |
| GPTQ all-Q4 target (96 + 96 calibration windows), Q5 drafter, 8-bit scales, two-level LM head | 267.7 |
| drafter fine-tuned on the quantized target's own outputs (LoRA, one run) | ≈275 |
| re-ranked drafter vocabulary shortlist, 3-bit LM-head screen, chunked GDN record, tree temperature 1.25 | 291.8 |
| GPTQ Q4 drafter projections on Ada GEMM routes | 298.6 |
| Q3 gate/up in layers 0–15 | 301.3 |
| drafter conv projections at Q4 | 303.5 |
| end-to-end scale tuning (e2e31), more Q3 | ≈307 |
| drafter MLP at Q3 | 309.9 |
| E2E v5 (16 more Q3 down layers) + INT8 V cache | 311–313 |
| GDN convolution fused into the input-projection epilogue | +0.4% (forced A/B) |

Some notes on the steps that taught something.

**Quantization was the biggest lever, and quality went up, not down.**
- The release container uses round-to-nearest Q4/Q5. GPTQ with act-order and a clip search already beats it at all-Q4,
  which is fewer bytes than the release.
- End-to-end scale tuning then trains only the per-group scales against the BF16 model's outputs. It buys enough KL
  headroom to move more projections to Q3.
- Code is 4× more sensitive than prose. Top-1 agreement, not KL, ends up being the binding constraint.

**A 3-bit screen in front of the LM head.**
- The 248k × 5120 head is streamed through a 3-bit "screen" that keeps the top-32 candidates per column.
- Only those candidates are rescored exactly.
- The screen alone was output-identical on all 480 prompts, and it runs at the DRAM roof: 927 GB/s at T = 1,
  895 GB/s at T = 16.

**Q3 kernels are limited by DRAM access pattern, not arithmetic.** Removing the MMA, the dequantization or the scale
math from the Q3 GEMM saved ≤ 1.3 µs. Removing *all* compute made it slower, because more resident CTAs scatter
requests across more DRAM pages. Repacking each pipeline stage into one contiguous tile was 5% faster, with bit-identical
outputs.

**The drafter is free to be imprecise.** Drafter precision cannot change the output; it only moves acceptance.
- Q4/Q3 drafter projections paid for themselves once the GEMM routes ran them at full bandwidth.
- Fine-tuning the drafter on the target's outputs gave +1.4% acceptance once.
- More rank, more epochs, soft labels and new data all landed at the same place.

## Quality: measure against FP32, not against the release

Every target change is scored on 46,059 next-token predictions (44 windows of 2,048 tokens, prose and code).
- The reference is FP32 compute over the BF16 checkpoint, layer-streamed through the transformers modules on the
  same 24 GB card.
- Metrics:
  - KL64: KL(ref‖candidate) on the reference's top-64 support, using the candidate's exact logits there;
  - top-1 agreement;
  - perplexity.

| | prose KL64 | code KL64 | KL64 | top-1 | PPL (ref 3.146) |
|---|---|---|---|---|---|
| release container | 0.0290 | 0.1095 | 0.0668 | 0.9250 | 3.294 |
| current target (E2E v5, Q3 mix, INT8 V) | 0.0265 | 0.1016 | 0.0618 | 0.9256 | 3.213 |

The bar for adoption is "better than the release on every split and metric". Top-1 has the least headroom: the
current target clears it by about 25 of 46,059 predictions.

A non-bit-exact kernel change, such as FP16 GDN state or a fused norm, flips about 200 near-tie predictions in each
direction, so it moves top-1 by about ±20. Rounding the carried GDN state to 5, 7, 8, 10 or 16 mantissa bits costs
10–25 agreements whatever the precision, which looks like noise around a lucky baseline, not damage. The next post
is about measuring the decode path itself, which the prefill-based tool never executes.

## Measuring 0.3%

Most late gains are 0.3–1%. Run-to-run noise on an unforced Spec-Bench run is bigger than that, and worse: a
near-tie flip changes which continuation is generated, and with it acceptance and tok/s. What worked:

1. **Forced text.** The engine can replace the target's greedy token with a reference id at each position
   (`NINFER_FORCE_TOKENS`). Every configuration then walks the same 480 texts, and round time is compared on
   identical tokens.
2. **A B A B on one GPU,** with the other GPU's load held constant and no builds anywhere on the box. A niced
   8-job build once made the same configuration read 0.9% slower.
   - A→C and B→D give the drift. It is often 0.1–0.3%, which is as large as the effect.
3. **Paired bootstrap per prompt** for the confidence interval on ms/round, tok/step and tok/s.
4. **nsys per-call kernel medians** to explain each result. nsys inflates host-side time severalfold, so host costs
   are priced from unprofiled request logs instead.

## What did not work

- Trellis quantization (EXL3): matching our scalar quality needs ≈3.75 bpw, −9% bytes at best, and the decoder is
  slower.
- A 32-node verify tree: +10% acceptance against +10–15% round time.
- Running GDN or attention side work on a second stream: the kernels share DRAM and stretch each other one-for-one.
- SM-balanced GEMM grids, `prefetch.global.L2` on Ada, NUMA pinning, splitting the CUDA graph: all null.
- A 2-bit head screen: top-1 recall 0.987.
- Folding RMSNorms into GEMM epilogues through a cross-CTA reduction. The producer GEMM grew 5.5 µs per call, more
  than the 80 removed norm launches saved; the likely cause is atomics landing on a single L2 line.
